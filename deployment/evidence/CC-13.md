# CC-13 all-Docker profile evidence

Date: 2026-09-08.

## Result

The renderer converts a validated all-Docker configuration and release inventory into Compose JSON. Every application image uses a repository digest. No service contains a build instruction.

The profile starts frontend, API, worker, edge, Kestra, Redis, and two PostgreSQL instances. One-shot services apply permissions, render private configuration, provision databases, migrate schema, and initialize bootstrap access. Runtime services wait for successful one-shot completion and healthy dependencies.

Only edge publishes port 443 in the production render. Frontend and API share the ingress bridge with edge. All stateful services remain on the internal bridge.

## Live profile verification

The retained `cc-fault-cc13` fixture used a loopback-only port 14443 override because another local service owns port 443. The production render retains port 443.

Verified HTTPS returned 401 without bootstrap credentials and 200 with valid credentials. The protected startup endpoint returned ready for application database, Kestra database, Redis, frontend, API, workers, artifacts, and Kestra.

Synthetic checks produced these results:

- Application migration count returned one.
- Redis accepted a namespaced cache marker.
- Worker dispatch returned 200 and a deterministic marker checksum.
- Artifact publication stored and read 21 bytes with SHA-256 `23023db1291377d4a62e4c54984d4a5d59d69ba37283864d930826ed5127a2f1`.
- Kestra stored flow `campus.validation/cc11_external_worker` and namespace file `/cc13-marker.txt`.

A full Compose down and up preserved PostgreSQL, artifact, and Kestra state. The Redis marker disappeared as required by discard-cache behavior. All eight startup checks returned ready after restart.

The CC-18 process fault harness interrupted API, worker, Redis, both PostgreSQL instances, Kestra, and artifact permissions.
The first run passed seven process checks and fourteen durable fixture checks.
The limited repeat passed the same checks after configured resource limits were added.
That harness covers component interruption only and does not qualify all CC-18 scenarios.

## Static checks

`deployment:profiles-test` passed through Nx. `docker compose config --quiet` accepted the root production render and the isolated render. Tests assert digest-only application images, one published edge port, PostgreSQL mount paths, absent Redis data volume, successful one-shot ordering, and configured resources.

## Stop and erase behavior

`docker compose down` preserved all named volumes during the restart test. `erase.mjs` requires `--confirm-data-loss` before adding `--volumes`.
The [CC-16 final-image fixture](CC-16-final-images-result.json) executed the installer erasure command against its isolated project.
The standalone `erase.mjs` wrapper has no separate execution record.

Automatic approval review rejected erasure of the earlier `campus-commander` fixture volumes. The review could not prove that every volume belonged to this task. Those volumes remain intact.

# CC-10 shared artifact storage

Date: 2026-09-08. Selected adapter: operator-provided POSIX shared filesystem.
NFSv4.1 is the district qualification candidate. No district server version or mount has been qualified.
The adapter reuses the local streaming and PostgreSQL publication implementation without a rename dependency.

Command:

```sh
CC_STORAGE_BACKEND=shared-filesystem npm exec nx run deployment:storage-integration
```

The complete synthetic suite passed through shared mode on the local host.
The suite includes writer and publisher process exits, metadata rollback, recovery, and cleanup rollback.
The consumer-container restart passed on that host.
These results do not establish cross-host visibility or district filesystem durability.

Remaining acceptance blockers:

- Two distinct district worker hosts with the same shared mount and application database.
- Selected filesystem server version, export configuration, and durable-write guarantees.
- Actual shared-mount outage, permission, interruption, concurrency, and restart evidence.
- Kubernetes storage class, PVC, CSI driver, and cross-node rescheduling evidence.

CC-10 remains incomplete until those infrastructure gates pass.

Subsequent [CC-15 workload evidence](CC-15-workload-result.json) records cross-node artifact reads and rescheduling in Kind.
Those nodes used one synthetic shared host directory.
That result does not qualify a district shared-filesystem backend or its failure behavior.

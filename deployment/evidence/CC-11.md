The isolated check used Kestra Open Source 1.3.37 and PostgreSQL 18.6.

## Pinned deployment configuration

Kestra used this Linux amd64 manifest:

`docker.io/kestra/kestra@sha256:c9e6551c671d8e13274b85f3ccafb945065b8e35e33cf2ea3eeff817d52e7114`

The worker used this local Linux amd64 image ID:

`sha256:783cadff46d82db53e52f8cde22672bcdac523b8d22cb75b72a155b503db6f65`

[`render-config.mjs`](../kestra/render-config.mjs) generated the Kestra configuration and runtime files.
It created one PostgreSQL datasource for database `kestra` and role `kestra`.
PostgreSQL supplied both the repository and queue.
The internal-storage path was `/app/storage` on a dedicated volume.

The renderer rejected plaintext endpoints for hybrid and Kubernetes profiles.
It converted the Kestra PEM certificate into a PKCS12 server keystore.
It converted the worker private CA into a PKCS12 truststore.
It wrote configuration, credentials, probe data, and keystores with mode 0600.

## Authentication and trust

The Kestra readiness route was `GET /api/v1/main/flows/search?size=1`.
It returned 401 without Basic Auth.
It returned 200 with the generated credential.
It returned 200 with the same credential after Kestra restarted.

The worker used HTTPS with a generated private certificate.
A client without the private CA failed TLS validation with curl exit 60.
The dispatch route returned 401 without a token.
It returned 401 with the wrong token.
It returned 400 when the authenticated body contained an unknown `command` field.

The test stored no credential in the flow, execution result, logs, or evidence file.
The flow resolved the dispatch token through Kestra Open Source secret environment support.
The flow resolved the worker URL through the Kestra environment context.

## External worker execution

[`cc11-external-worker.yaml`](../kestra/cc11-external-worker.yaml) used two built-in core tasks.
The HTTP Request task called `POST /dispatch/synthetic` on the independent worker.
The Storage Write task persisted the redacted worker response in Kestra internal storage.

Execution `rfFiBuUzuB0bbsi1QtzL9` used correlation ID `cc11-22167-528719`.
The flow upload returned 200.
The worker accepted the first dispatch and entered an eight-second synthetic delay.
The harness sent `SIGKILL` to that worker before completion.

Kestra retried after the worker restarted.
The second dispatch returned the same correlated checksum.
The execution reached `SUCCESS` after two dispatch attempts.
One worker attempt completed.
Recovery took 13 seconds.
The flow limited settlement to three attempts or 30 seconds.

The task wrote this internal-storage object:

`kestra:///campus/validation/cc11-external-worker/executions/rfFiBuUzuB0bbsi1QtzL9/tasks/persist-result/43lbYOwBxJZ4CaDpkzMpBF/11421281452168577432.json`

This behavior provides at-least-once dispatch.
The synthetic endpoint keeps no durable deduplication record.
The result does not establish exactly-once external effects.

## Internal-storage restart

The harness created a namespace directory and uploaded a marker through authenticated APIs.
Both operations returned 200.
The marker checksum before restart was:

`0f0e0c3a4a44d4a3c179e13512ce9352f1674331ea8657ecb7fae405f2d57add`

The harness restarted Kestra with the same database and internal-storage volumes.
The marker returned the same checksum after restart.
The execution and namespace marker used only Kestra internal storage.
The renderer does not configure Campus Commander application artifact storage.

This check ran on one Docker host.
It does not prove shared-filesystem access from separate hosts.
It does not prove Kubernetes pod rescheduling against a ReadWriteMany storage class.

## Database startup failure

[`database-failure-result.json`](../kestra/database-failure-result.json) records the isolated failure check.
The check configured one PostgreSQL datasource with an invalid Kestra role password.
PostgreSQL rejected the authentication attempt.
Kestra kept retrying, so the harness ended the process after 20 seconds.

Exit status 124 records the harness timeout.
It does not represent a Kestra exit code.
The check recorded only the safe failure summary.
It recorded no invalid or valid password.

## PostgreSQL observation

Kestra applied its schema through version 1.57 on PostgreSQL 18.6.
It completed the synthetic execution without a database error.

Kestra logged this warning twice:

> Flyway upgrade recommended: PostgreSQL 18.6 is newer than this version of Flyway and support has not been tested. The latest supported version of PostgreSQL is 17.

This result establishes measured compatibility for the tested path.
It does not establish vendor-certified PostgreSQL 18 support.

## Unmet acceptance evidence

- No second host or district shared mount was available for distributed storage verification.
- No Kubernetes context or ReadWriteMany storage class was available for pod rescheduling.
- The worker endpoint supports only the harmless synthetic contract.
- The worker has no durable deduplication record for external effects.
- The database failure check covered one authentication failure path.

These gaps block the distributed-storage portion of CC-11.
They also block any exactly-once or production external-effect claim.

# CC-14 hybrid profile evidence

Date: 2026-09-08.

## Result

The hybrid renderer maps validated service placement into controller and worker-host Compose files.
It omits every external service replacement and keeps each selected local service.

The checked example uses district PostgreSQL and Redis.
It keeps local frontend, API, edge, Kestra, and two worker hosts.

## Placement and ownership

The supported placement matrix is documented in `deployment/profiles/hybrid/README.md`.
Application and Kestra PostgreSQL must share local or external ownership.
Distributed workers require district PostgreSQL.

External Kestra removes the Kestra workload, configuration helper, dependencies, and storage mounts.
Local Redis retains its configuration helper, discard-cache storage, TLS material, and health dependency.

The controller renderer omits workers when `host.workerHosts` exceeds one.
It writes one worker Compose file per declared host.
Each worker file binds only an explicit non-loopback district address.

## Security and readiness

Frontend, API, worker, PostgreSQL, Redis, Kestra, and edge listeners use verified TLS where selected.
Application images inherit health checks that verify the configured DNS name and certificate authority.

Each service mounts only its required credentials and certificate files.
The migration service retains the operator migrator credential.
API and worker artifact mounts use the configured shared path as the container path.

The storage preflight runs as UID 1000.
It checks read, write, and search access without changing district-owned paths.

The controller keeps the application service network internal.
The ingress network accepts the published edge HTTPS listener.
Only services that contact district endpoints join the egress network.
The operator must restrict edge ingress and district egress through the host firewall.
